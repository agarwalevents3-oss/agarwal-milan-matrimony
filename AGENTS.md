# Working in this repository

Read `docs/STATUS.md` first — it says what is built and what is not.
`docs/DECISIONS.md` explains why the architecture looks the way it does.

## Before you push

```bash
npm run check    # typecheck + lint + schema verification + tests
```

## Rules that are not negotiable

1. **Authorisation belongs in the database.** The anon key is public by design,
   so RLS policies and triggers — not route guards — are what protect user data.
   If you add a table, enable RLS and add a test in `tests/db/`.
   `npm run verify:schema` fails on any public table without RLS.

2. **The service-role key is read in exactly one file** (`lib/supabase/admin.ts`).
   A lint rule blocks `process.env` elsewhere, and `npm run verify:no-secrets`
   scans built browser bundles. Never give a secret a `NEXT_PUBLIC_` prefix.

3. **After changing a migration, run `npm run gen:types`.** `types/database.ts`
   is generated by introspecting the schema and must be regenerated, or the
   types silently drift.

4. **Never weaken these without saying so explicitly:** Aadhaar immutability,
   the "no verification without successful payment" rule, the one-match-per-pair
   constraint, and the rule that a member never sees another member's phone
   number. Each is enforced in the database and covered by tests.

5. **Reads go direct to Supabase under RLS; only rule-bearing writes get a Route
   Handler.** That is what keeps serverless invocations — and the bill — low.

## Conventions

- Validation schemas in `lib/validation/` are shared by client and server. Add
  to the shared schema rather than validating twice.
- Route Handlers are built with `route()` from `lib/api/handler.ts`, which
  declares access, rate limits and the body schema. Do not hand-roll auth checks.
- Errors go through `lib/utils/errors.ts`. Raw database messages must never
  reach a user.
