# Build status

Written for the team picking this up. Honest account of what works, what is
stubbed, and what has not been verified.

Last updated: 2026-09-18.

---

## The one caveat that matters

**Nothing here has been run against a live Supabase project.** No Supabase
credentials existed during this build, and Docker was unavailable, so the local
Supabase stack could not be started either.

What was done instead: every migration is applied to a **real Postgres**
(PGlite, Postgres compiled to WASM) on every test run, with Supabase's `auth`
and `storage` schemas stubbed to match their real shapes. That is genuine
verification of the SQL — it found two real bugs during this build — but it is
not a substitute for a first run against the hosted product.

Expect to spend a session on these when you connect a project:

| Risk | Why | If it bites |
|---|---|---|
| Phone provider may need SMS credentials to enable | Supabase's dashboard sometimes requires an SMS provider before phone auth can be turned on | Switch `STRATEGY` in `lib/auth/identity.ts` to `"synthetic-email"`. That file is the only thing that changes. |
| Storage `list()` metadata shape | `verifyUploadedObject()` reads `size` and `mimetype` from `storage.list()` | Adjust the field names in `lib/services/storage.ts` |
| `app_metadata.role` claim in the JWT | `is_admin()` reads it; the shape is stable but unverified here | Confirm with a real token, then adjust the path in migration 0003 |

## Built and tested

### Foundation
- Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4
- Four Supabase clients, each with a clear job: browser, cookie-server,
  session-less anon (cacheable), service-role
- Session proxy with coarse status-based redirects
- `types/database.ts` **generated by introspecting the migrations**, so types
  cannot drift from the schema
- GitHub Actions CI: typecheck, lint, schema verification, tests, build, secret
  scan, and migration push to production on `main`

### Database — 8 migrations, all verified
18 tables · 33 RLS policies · 22 functions · 14 triggers · 48 indexes · 4 buckets

Business rules that are **database guarantees**, not application conventions:
- registration state machine, with illegal transitions rejected by trigger
- an unpaid registration cannot be verified, at any layer
- Aadhaar is immutable and undeletable — including by the service role
- one interest per direction; one match per pair, enforced by constraints
- match creation is a single transaction, so concurrent accepts cannot
  double-write
- name, gender and date of birth lock once set
- `REG000001` ids come from a Postgres sequence, so they cannot be forged

### Public website
Home and Contact are **static with hourly ISR**, driven entirely from
`site_content` / `faqs` rows. An admin edit invalidates by tag — no redeploy,
and effectively no serverless cost.

### Registration — complete, end to end
Mobile → OTP → account → profile → documents → submit → payment.

- OTP service with HMAC-hashed codes, 10-minute expiry, 5-attempt cap, 60-second
  resend cooldown and per-phone/per-IP rate limits. Mock driver now; MSG91
  driver written and inert.
- Client-side WebP compression into two renditions before upload. **This is what
  keeps the project inside the free tier's 1 GB** — roughly 120 KB per member
  instead of 3–5 MB.
- Aadhaar consent captured as evidence: the exact text shown, timestamp and IP.

### Payment — complete against the mock gateway
Provider seam with `MockPaymentProvider` and a **fully written**
`RazorpayProvider` (both signature checks implemented as Razorpay documents
them). The mock signs for real and goes through the same verification route, so
the state machine is the one Razorpay will drive. Webhook handler is idempotent.

### API surface — all routes written and typechecked
OTP send/verify · register account/draft/submit · payment create/verify/webhook ·
profile update/photo · interest send/respond · notifications read ·
admin verify/reject/suspend/delete · cron cleanup

### Tests — 76, all passing
| Suite | Count | Covers |
|---|---|---|
| `tests/db/rls.test.ts` | 17 | Every privacy promise in the PRD |
| `tests/db/business-rules.test.ts` | 25 | State machine, Aadhaar lock, interests, matches |
| `tests/db/registration-flow.test.ts` | 8 | Draft → submit → payment → verification |

### Guard rails, both verified firing

- `verify:no-secrets` scans built browser bundles for every server secret

## Suggested order

1. Connect a Supabase project and work through the risk table above. Everything
   else depends on knowing the platform behaves as assumed.
2. Admin panel (#5) — without it nobody can be verified, so no other authenticated
   screen can be exercised with real data.
3. Search and grid (#6) — the heart of the product.
4. Interests, matches and notifications (#8, #9) — they share components.
5. Profile editing (#7) and the admin CMS (#10).
6. E2E tests once there is a full path to walk.
