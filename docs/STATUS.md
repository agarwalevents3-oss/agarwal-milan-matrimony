### The phone-auth finding

The plan called for Supabase's native phone identity. Tested directly:
`admin.createUser` with a phone identity succeeds, but the actual login call —
`signInWithPassword({ phone, password })` — is rejected with
`phone_provider_disabled`. Enabling the toggle in the dashboard turns out to
require real Twilio (or another SMS provider's) credentials before Supabase
will even save the setting, despite our own OTP service being what actually
verifies the number.

Since setting up Twilio is explicitly deferred, we switched to the
**synthetic-email identity** (`{mobile}@phone.internal`) via a new
`AUTH_IDENTITY_STRATEGY` environment variable. **This was also verified
end-to-end against the live project**: created a user, signed in, got a valid
session back, then deleted the test user. Full account of the decision and the
trade-off (a future real-SMS integration goes through the application-layer OTP
service, not a Supabase Auth Hook) is in `docs/DECISIONS.md` §13.

## What is built

### Foundation
- Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4
- Four Supabase clients, each with a clear job: browser, cookie-server,
  session-less anon (cacheable), service-role
- Session proxy with status-based redirects
- `types/database.ts` **generated by introspecting the migrations**, so types
  cannot drift from the schema
- Security headers including a CSP scoped to Supabase
- CI: typecheck, lint, schema verification, unit + database tests, build, secret
  scan, end-to-end tests, and migration push to production on `main`

### Database — 9 migrations
18 tables · 34 RLS policies · 25 functions · 14 triggers · 48 indexes · 4 buckets

Business rules that are **database guarantees**, not application conventions:
- registration state machine, with illegal transitions rejected by trigger
- an unpaid registration cannot be verified, at any layer
- Aadhaar is immutable and undeletable — including by the service role
- one interest per direction; one match per pair, enforced by constraints
- match creation is a single transaction, so concurrent accepts cannot
  double-write
- name, gender and date of birth lock once set
- `REG000001` ids come from a Postgres sequence, so they cannot be forged
- admin reporting functions re-check `is_admin()` internally

### Public website
Home and Contact are **static with hourly ISR**, driven entirely from
`site_content` / `faqs` rows, with empty sections hidden rather than rendered
blank. An admin edit invalidates by tag — no redeploy.

### Registration — complete
Mobile → OTP → account → profile → documents → submit → payment.

- OTP service with HMAC-hashed codes, 10-minute expiry, 5-attempt cap,
  60-second resend cooldown and per-phone/per-IP rate limits. Mock driver now;
  MSG91 driver written and inert.
- Client-side WebP compression into two renditions before upload — roughly
  120 KB per member instead of 3–5 MB.
- Aadhaar consent captured as evidence: exact text shown, timestamp and IP.

### Payment — complete against the mock gateway
Provider seam with `MockPaymentProvider` and a fully written `RazorpayProvider`
(both signature checks implemented as Razorpay documents them). The mock signs
for real and goes through the same verification route. Webhook is idempotent.

### Member application
- **Discovery**: server-rendered search over an indexed view, filters held in
  local state until DONE, 20 results per page paginated in the database,
  filters in the URL so searches are shareable
- **Profile detail**: permitted information only, with the admin contact number
  shown in place of personal numbers
- **Interests**: send, accept, decline, with optimistic UI
- **Matches**: mutual matches, with contact still routed through the team
- **Own profile**: view, edit optional fields, replace photo; identity and
  Aadhaar shown as locked
- **Notifications**: full list with deep links, plus a live unread badge over
  Supabase Realtime

### Admin panel — complete
- Dashboard with eleven metrics and a recent-activity feed
- Registration queue: search by ID, name, mobile or email; filter by status;
  paginated in the database; table on desktop, cards on mobile
- Member detail: complete record, private documents behind five-minute signed
  URLs with every view audit-logged, and verify / reject / suspend / delete —
  with **no way to edit member data**, matching both the PRD and the database
- Interest and match oversight
- CMS for every section of the public site, saved per section
- FAQ management: add, edit, delete, reorder, show/hide
- Website imagery: upload, replace and remove the home page hero and couple
  images, with alt text, compressed on upload and served from the CDN
- Settings: the member-facing contact number, the registration fee, and a
  live/test indicator for the OTP and payment integrations
